# Организации — REST API v2

Реализация технического задания «Команды REST организации (v1.2)»
(`docs/Команды REST организации (v1.2).docx`).

Базовый путь: `/api/v2/organizations`. Формат обмена: `application/json; charset=utf-8`.
Организация — узел иерархического справочника подразделений; корневые организации
имеют `parent = null`, глубина иерархии не ограничена.

## Маршруты

| № | Команда | Метод | URI | Успех | Права |
|---|---|---|---|---|---|
| 1 | Добавить организацию | `POST` | `/api/v2/organizations` | 201 | администратор |
| 2 | Получить организацию | `GET` | `/api/v2/organizations/{divcode}` | 200 | чтение |
| 3 | Получить список | `GET` | `/api/v2/organizations` | 200 | чтение |
| 4 | Изменить организацию | `PUT` | `/api/v2/organizations/{divcode}` | 200 | администратор |
| 5 | Обновить организацию | `PATCH` | `/api/v2/organizations/{divcode}` | 200 | администратор |
| 6 | Удалить организацию | `DELETE` | `/api/v2/organizations/{divcode}` | 204 | администратор |
| 7 | Получить категории доступа организации | `GET` | `/api/v2/organizations/{divcode}/accessnames` | 200 | чтение |

`PUT` заменяет все изменяемые поля (`name`, `parent`, `flag`), `PATCH` — только переданные.

## Авторизация

Все команды требуют заголовок `Authorization: Bearer <token>`.

Токен выдаёт `GET /login?username=ADMIN&pasword=333`:

* `username=ADMIN` — токен с ролью `admin`: доступны и чтение, и изменения;
* любой другой логин с паролем `333` — роль `user`: только чтение.

Изменяющие команды (`POST`, `PUT`, `PATCH`, `DELETE`) защищены политикой `Admin`.
Отсутствие или порча токена даёт `401 UNAUTHORIZED`, недостаточная роль — `403 FORBIDDEN`;
оба ответа приходят в общем формате ошибки.

## Модель организации

| Поле | Тип | Описание |
|---|---|---|
| `id` | integer | Внутренний идентификатор записи (`ORGANIZATION.ID_ORG`) |
| `divcode` | string | Уникальный код организации, 1–50 символов: латиница, цифры, `-`, `_`, `.`; не изменяется |
| `name` | string | Название, 1–50 символов после обрезки пробелов |
| `parent` | string \| null | Код родительской организации; `null` — корневая |
| `flag` | integer | `0` — обычная, `1` — гостевая |
| `createdAt` | string \| null | Дата создания, ISO 8601 UTC; `null`, если в базе нет отметки |
| `updatedAt` | string \| null | Дата последнего изменения, ISO 8601 UTC |

`id`, `createdAt` и `updatedAt` в теле запроса не передаются и игнорируются.
Неизвестные поля игнорируются, имена полей — `camelCase`, регистр значим.

## Формат ошибки

Все ответы с кодом 4xx и 5xx содержат объект:

```json
{
  "error": "VALIDATION_ERROR",
  "message": "Поле divcode обязательно",
  "details": [
    { "field": "divcode", "issue": "required" }
  ]
}
```

`details` — необязательный массив уточнений (`field`, `issue`). У конфликтов
удаления вместо `details` возвращаются `children` и `people` (см. DELETE).

## 1. Добавить организацию — `POST /api/v2/organizations`

```json
{
  "divcode": "ORG-001",
  "name": "ООО «Пример»",
  "parent": "ORG-000",
  "flag": 0
}
```

* `divcode` обязателен, уникален без учёта регистра; дубликат — `409 DUPLICATE_DIVCODE`;
* `name` обязателен, обрезается от пробелов;
* `parent` необязателен: не указан (или `null`, или пустая строка) — организация корневая;
  несуществующий код — `422 PARENT_NOT_FOUND`;
* `flag` необязателен, по умолчанию `0`; допустимы только `0` и `1`, иначе `400`.

Ответ `201 Created`, заголовок `Location: /api/v2/organizations/ORG-001` и тело созданной
организации.

## 2. Получить организацию — `GET /api/v2/organizations/{divcode}`

```json
{
  "id": 101,
  "divcode": "ORG-001",
  "name": "ООО «Пример»",
  "parent": "ORG-000",
  "flag": 0,
  "createdAt": "2026-11-20T10:00:00Z",
  "updatedAt": "2026-11-20T10:00:00Z"
}
```

Поиск по `divcode` не зависит от регистра. Не найдено — `404 NOT_FOUND`,
некорректный `divcode` — `400 VALIDATION_ERROR`.

## 3. Получить список — `GET /api/v2/organizations`

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `parent` | string | — | Фильтр по коду родителя. Пустое значение (`parent=`) — только корневые |
| `name` | string | — | Поиск по подстроке в названии без учёта регистра |
| `page` | integer | 1 | Номер страницы, начиная с 1 |
| `pageSize` | integer | 20 | Размер страницы, от 1 до 100 |
| `sort` | string | `name` | `name`, `-name`, `divcode`, `-divcode`, `createdAt`, `-createdAt`; `-` — по убыванию |

```json
{
  "items": [
    {
      "id": 101,
      "divcode": "ORG-001",
      "name": "ООО «Пример»",
      "parent": "ORG-000",
      "flag": 0,
      "createdAt": "2026-11-20T10:00:00Z",
      "updatedAt": "2026-11-20T10:00:00Z"
    }
  ],
  "page": 1,
  "pageSize": 20,
  "total": 1
}
```

`total` — число записей, удовлетворяющих фильтру, а не число страниц. Если записей нет,
возвращается `200` с пустым `items`. Несуществующий `parent` даёт пустой список,
некорректные `page`, `pageSize` или `sort` — `400 VALIDATION_ERROR`.

Поиск по `name` экранирует символы `%`, `_` и `\`, поэтому они не работают как шаблоны.

## 4. Изменить организацию — `PUT /api/v2/organizations/{divcode}`

```json
{
  "name": "ООО «Пример»",
  "parent": "ORG-000",
  "flag": 1
}
```

* `name` обязателен;
* `parent` необязателен: если не передан или `null` — организация становится корневой;
* `flag` необязателен: если не передан — `0`;
* `divcode` в теле не нужен; если передан и не совпадает с путём (без учёта регистра) —
  `400 DIVCODE_IMMUTABLE`;
* существование родителя проверяется (`422 PARENT_NOT_FOUND`), циклы запрещены
  (`409 CYCLE`).

Ответ `200 OK` — обновлённая организация; `updatedAt` изменяется, `createdAt` остаётся
прежним (при наличии колонки `DATE_CREATE`, см. раздел «Миграции»).

## 5. Обновить организацию — `PATCH /api/v2/organizations/{divcode}`

```json
{
  "name": "ООО «Пример-2»",
  "flag": 1
}
```

* требуется хотя бы одно изменяемое поле (`name`, `parent`, `flag`), иначе `400 EMPTY_PATCH`;
* `name` нельзя передать пустым или `null` — `400 VALIDATION_ERROR`;
* `parent = null` перемещает организацию в корень; строка — код существующей организации
  (проверки как в `PUT`);
* `flag` не может быть `null`; допустимы `0` и `1`;
* `divcode` изменять нельзя: значение, отличное от пути, даёт `400 DIVCODE_IMMUTABLE`;
  совпадающее значение игнорируется и не считается изменяемым полем.

Ответ `200 OK` — обновлённая организация.

## 6. Удалить организацию — `DELETE /api/v2/organizations/{divcode}`

Удаление разрешено только при отсутствии дочерних организаций и активных сотрудников
(`PEOPLE.ACTIVE = 1`) организации.

Порядок работы: строка организации блокируется (`SELECT ... WITH LOCK`) в транзакции,
затем проверяются дочерние организации и сотрудники, после чего выполняется физическое
удаление. Обе проверки выполняются до принятия решения.

| Ситуация | Ответ |
|---|---|
| Удалено | `204 No Content` без тела |
| Организации нет | `404 NOT_FOUND` |
| Есть дочерние организации | `409 HAS_CHILDREN` |
| Есть активные сотрудники | `409 HAS_PEOPLE` |
| Есть и то, и другое | `409 HAS_CHILDREN_AND_PEOPLE` |
| Организация корневая (`ID_ORG = 1`) | `409 ROOT_ORGANIZATION` |

Пример `409 HAS_CHILDREN`:

```json
{
  "error": "HAS_CHILDREN",
  "message": "Удаление невозможно: у организации есть дочерние организации",
  "divcode": "ORG-001",
  "childrenCount": 2,
  "children": ["ORG-002", "ORG-003"]
}
```

Пример `409 HAS_CHILDREN_AND_PEOPLE`:

```json
{
  "error": "HAS_CHILDREN_AND_PEOPLE",
  "message": "Удаление невозможно: у организации есть дочерние организации и сотрудники",
  "divcode": "ORG-001",
  "childrenCount": 2,
  "children": ["ORG-002", "ORG-003"],
  "peopleCount": 2,
  "people": ["P-100", "P-101"]
}
```

Значения `people` — табельные номера (`PEOPLE.TABNUM`), как и в остальном API v2.
Повторный `DELETE` уже удалённой организации возвращает `404`. Каскадного удаления нет.
Неактивные сотрудники (`ACTIVE = 0`) при удалении организации переводятся в родительскую
организацию триггером БД `ORGANIZATION_PEOPLESETPARENTID` и тоже становятся неактивными.

`DELETE` корневой организации (корень `ID_ORG = 1`, `DIVCODE = 'dv_All'`) запрещён:
её удаление разрушает ссылки `ID_PARENT = 1` у остальных записей и корень дерева.
Это ограничение добавлено к перечню ТЗ отдельным кодом `409 ROOT_ORGANIZATION`.

## 7. Получить категории доступа организации — `GET /api/v2/organizations/{divcode}/accessnames`

Возвращает список идентификаторов категорий доступа, привязанных к организации
в таблице связей `SS_ACCESSORG`.

```json
[2, 5]
```

* значения — `id_accessname` из `ACCESSNAME`, по возрастанию, без дубликатов;
* если связей нет — `200` и пустой массив `[]`;
* организация не найдена — `404 NOT_FOUND`, некорректный `divcode` — `400 VALIDATION_ERROR`;
* если в базе отсутствует таблица `SS_ACCESSORG` (старый шаблон `EMPTY.gdb`),
  связей нет и метод возвращает `[]`.

Метод только читает связи: создание и удаление связей организации с категориями
доступа выполняется в конфигураторе БД, API эти операции не предоставляет.

## Коды ответов

| HTTP | `error` | Когда возвращается |
|---|---|---|
| 200 | — | Команда выполнена: GET, PUT, PATCH |
| 201 | — | Организация создана: POST |
| 204 | — | Организация удалена: DELETE |
| 400 | `VALIDATION_ERROR` | Ошибка валидации полей, некорректные `page`, `pageSize`, `sort`, пустое тело |
| 400 | `INVALID_JSON` | Тело запроса не разбирается как JSON или не является объектом |
| 400 | `DIVCODE_IMMUTABLE` | Попытка изменить `divcode` |
| 400 | `EMPTY_PATCH` | `PATCH` не содержит ни одного изменяемого поля |
| 401 | `UNAUTHORIZED` | Токен отсутствует, просрочен или неверен |
| 403 | `FORBIDDEN` | Нет прав администратора |
| 404 | `NOT_FOUND` | Организация не найдена |
| 409 | `DUPLICATE_DIVCODE` | `divcode` уже существует |
| 409 | `CYCLE` | Ссылка `parent` образует цикл |
| 409 | `HAS_CHILDREN` | У организации есть дочерние организации |
| 409 | `HAS_PEOPLE` | В организации есть активные сотрудники |
| 409 | `HAS_CHILDREN_AND_PEOPLE` | Есть и дочерние организации, и активные сотрудники |
| 409 | `ROOT_ORGANIZATION` | Попытка удалить корневую организацию |
| 422 | `PARENT_NOT_FOUND` | Родительская организация не существует |
| 500 | `INTERNAL_ERROR` | Внутренняя ошибка сервера |

`409` — конфликт состояния (дубликат, цикл, непустая организация), `422` — семантически
некорректная ссылка на родителя, `400` — ошибка формата и валидации. Ответы 4xx не содержат
внутренних деталей; ошибки 500 логируются.

## Соответствие базе данных

API работает с одной базой (`ID_DB = 1`), как и остальные методы v2.

| API | `ORGANIZATION` |
|---|---|
| `id` | `ID_ORG` (первичный ключ вместе с `ID_DB`, генератор `GEN_ORG_ID`) |
| `divcode` | `DIVCODE` (`VARCHAR(50)`, `NOT NULL`) |
| `name` | `NAME` (`VARCHAR(50)`) |
| `parent` | `ID_PARENT`; `parent = null` ↔ `ID_PARENT = 1` (корень `ID_ORG = 1`, `DIVCODE = 'dv_All'`) |
| `flag` | `FLAG` (`SMALLINT`, по умолчанию `0`) |
| `updatedAt` | `TIME_STAMP` (обновляется при каждом изменении) |
| `createdAt` | `DATE_CREATE`, если колонка есть; иначе `TIME_STAMP` |
| — | `SS_ACCESSORG (ID_ACCESSORG, ID_DB, ID_ORG, ID_ACCESSNAME)` — связи организации с категориями доступа (`ID_ORG` → `ORGANIZATION`, `ID_ACCESSNAME` → `ACCESSNAME`); читаются методом `GET .../{divcode}/accessnames` |

`DIVCODE` уникален без учёта регистра на уровне API. Уникальный индекс
`UNQ_ORGANIZATION_DIVCODE (DIVCODE, ID_DB)` регистрозависим: Firebird 1.5 не поддерживает
индекс по выражению `UPPER(DIVCODE)`. Поэтому при одновременном создании `ORG-1` и `org-1`
из разных запросов возможна гонка — как и у `tabnum` в остальном API v2. Для строгой
гарантии нужен триггер `BEFORE INSERT OR UPDATE` с проверкой `UPPER(DIVCODE)`, который
выполняется в той же транзакции, что и вставка.

Служебные поля `ID_DEF_ACCESSNAME` и `TIME_STAMP`/`DATE_CREATE` API не изменяет, кроме
`TIME_STAMP` (обновление при `PUT`/`PATCH`) и `DATE_CREATE` (заполнение при вставке).

У организаций нет колонки признака активности (`ACTIVE` есть только у `PEOPLE`), поэтому
все найденные по `divcode` организации считаются активными, а условие ТЗ «найти активную
организацию» сводится к поиску существующей записи.

## Миграции

Файлы находятся в `docs/migrations` и выполняются вручную (Firebird 1.5, диалект 3).

| Файл | Назначение | Обязательность |
|---|---|---|
| `2026-11-22_organization_divcode_unique.sql` | Уникальный индекс `UNQ_ORGANIZATION_DIVCODE (DIVCODE, ID_DB)` | рекомендуется |
| `2026-11-22_organization_date_create.sql` | Колонка `DATE_CREATE` — неизменяемая дата создания | необязательно |

Без `DATE_CREATE` API возвращает `createdAt = updatedAt = TIME_STAMP`, то есть `createdAt`
меняется при каждом изменении организации. Наличие колонки проверяется автоматически при
первом запросе, перезапуск после миграции не требуется только на новом процессе: колонка
определяется один раз за время жизни процесса.

## Проверка

Дымовой тест контракта (134 проверки) — `docs/smoke-tests/organizations.ps1`:

```powershell
powershell -ExecutionPolicy Bypass -File docs\smoke-tests\organizations.ps1 `
    -BaseUrl http://localhost:5056
```

Скрипт создаёт и удаляет организации с кодами `T-*` и сотрудников с `tabnum T-*`,
поэтому запускать его следует на тестовой базе.
