# Идентификаторы в REST API v2: статистика и фильтры (версия 1.8.0)

Документ описывает методы v2 для таблицы `CARD`, добавленные в версии **1.8.0**:

| Метод | Маршрут | Назначение |
|---|---|---|
| GET | `/api/v2/Identifier/GetCount` | Количество записей `CARD` по фильтрам: всего, активных и неактивных |
| GET | `/api/v2/Identifier/GetList` | Постраничный список идентификаторов по тем же фильтрам |

Оба метода только читают данные и не требуют токена. Сотрудник, как и в
остальных методах v2, задаётся табельным номером `tabnum`; внутренний
`ID_PEP` в ответах не возвращается.

## Источник данных

Данные хранятся в таблице `CARD`:

| Колонка | Назначение |
|---|---|
| `ID_CARD` | номер карты (идентификатор) |
| `ID_CARDTYPE` | тип идентификатора (`CARDTYPE.ID`) |
| `ID_PEP` | внутренний идентификатор сотрудника |
| `ID_DB` | идентификатор базы |
| `TIMESTART` | начало действия идентификатора |
| `TIMEEND` | окончание действия; `NULL` — без ограничения |
| `ACTIVE` | признак активности: `1` — активен, `0` — неактивен |
| `CREATEDAT` | дата и время создания записи |

Список и статистика строятся по тому же соединению, что и раньше:

```sql
FROM CARD c
JOIN PEOPLE p ON p.ID_PEP = c.ID_PEP AND p.ID_DB = c.ID_DB
```

Поэтому в выборку попадают только карты, для которых в `PEOPLE` есть
сотрудник с тем же `ID_DB`. Отдельного фильтра по `ID_DB` нет: учитываются
все базы, представленные в таблицах.

## Общие фильтры

Оба метода принимают одни и те же необязательные query-параметры. Если
параметр не указан, фильтр по этому полю не применяется.

| Параметр | Поле | Правила |
|---|---|---|
| `tabnum` | `PEOPLE.TABNUM` | Точное совпадение; пробелы по краям обрезаются; до 50 символов. Если сотрудник не найден, результат пустой (не `404`). |
| `timestart` | `CARD.TIMESTART` | Дата или дата-время. Только дата — весь день; дата-время — точное совпадение. |
| `timeend` | `CARD.TIMEEND` | Дата или дата-время. Только дата — весь день; дата-время — точное совпадение. Записи с `NULL` под фильтр не попадают. |
| `active` | `CARD.ACTIVE` | `1`/`true`/`active` — только активные; `0`/`false`/`inactive` — только неактивные; пусто, `all`, `any` — все. |
| `id_cardtype` | `CARD.ID_CARDTYPE` | Целое неотрицательное число. В типовой базе типы 1–5 (`CARDTYPE.ID`). |
| `createdat` | `CARD.CREATEDAT` | Дата или дата-время. Только дата — весь день; дата-время — точное совпадение. `NULL` под фильтр не попадает. |

`GetList` дополнительно сохраняет прежний фильтр `identifire` — точное
совпадение с `CARD.ID_CARD`.

### Даты: только дата и дата-время

Для `timestart`, `timeend` и `createdat` действует одно правило:

* передана **только дата** (например, `2026-11-25` или `25.11.2026`) —
  выбираются записи за весь этот день, то есть
  `поле >= 2026-11-25 00:00:00 AND поле < 2026-11-26 00:00:00`;
* переданы **дата и время** (например, `2026-11-25 18:00:00` или
  `2026-11-25T18:00:00`) — выбираются записи с точным значением поля.

Значения разбираются как ISO 8601, а при неудаче — в текущей культуре
сервера. Некорректная дата даёт `400 VALIDATION_ERROR` с именем поля.

## GET /api/v2/Identifier/GetCount — статистика по CARD

```http
GET /api/v2/Identifier/GetCount?id_cardtype=1&active=1
```

Ответ:

```json
{
  "total": 12,
  "active": 10,
  "inactive": 2
}
```

| Поле | Что означает |
|---|---|
| `total` | Количество записей `CARD`, удовлетворяющих всем переданным фильтрам |
| `active` | Из них записей с `ACTIVE = 1` |
| `inactive` | Из них записей с `ACTIVE = 0` |

Правила:

* Все три числа считаются **после применения всех фильтров**, включая
  `active`. Например, при `active=1` ответ будет
  `{"total":10,"active":10,"inactive":0}`.
* Без фильтров метод возвращает статистику по всей таблице `CARD`.
* `ID_CARDTYPE` не обязателен: без него считаются все типы.
* Записи с `ACTIVE IS NULL` входят в `total`, но не входят ни в `active`,
  ни в `inactive` (в типовой схеме `ACTIVE` обязателен).
* Ошибка базы данных — `500 INTERNAL_ERROR`.

## GET /api/v2/Identifier/GetList — список идентификаторов

```http
GET /api/v2/Identifier/GetList?pageIndex=0&pageSize=10&id_cardtype=1&active=1&tabnum=T-100
```

Ответ — та же структура `Pagination`, что и раньше:

```json
{
  "context": [
    {
      "id_card": "A1B2C3D4",
      "id_cardtype": "1",
      "tabnum": "T-100",
      "timestart": "2026-11-25T19:19:53.3811",
      "timeend": null,
      "active": 1,
      "createdat": "2026-11-20T10:00:00"
    }
  ],
  "pageIndex": 0,
  "pageSize": 10,
  "pageCount": 1
}
```

Поля элемента:

| Поле | Тип | Источник |
|---|---|---|
| `id_card` | string | `CARD.ID_CARD` |
| `id_cardtype` | string | `CARD.ID_CARDTYPE` (для совместимости со старым ответом — строка) |
| `tabnum` | string | `PEOPLE.TABNUM` |
| `timestart` | string (ISO 8601) | `CARD.TIMESTART` |
| `timeend` | string \| null | `CARD.TIMEEND` |
| `active` | number \| null | `CARD.ACTIVE` |
| `createdat` | string \| null | `CARD.CREATEDAT` |

Правила:

* `pageIndex` — номер страницы с нуля; отрицательное значение приводится к 0.
* `pageSize` — от 1 до 1000; `0`, отрицательное значение или отсутствие
  параметра дают 10, больше 1000 — 1000.
* `pageCount` считается от количества записей **после фильтров**.
* Записи упорядочены по `CARD.ID_CARD`, затем по `CARD.ID_DB`, поэтому
  страницы не пересекаются.
* `id_pep` в ответе не возвращается.
* Без новых параметров метод работает как раньше: возвращает все карты,
  доступные через соединение с `PEOPLE`, с прежними полями
  `id_card`, `id_cardtype`, `tabnum`; поля `timestart`, `timeend`, `active`,
  `createdat` добавлены как расширение ответа.
* Ошибка базы данных — `500 INTERNAL_ERROR`.

## Ошибки

Ошибки валидации возвращаются в едином формате v2:

```json
{
  "error": "VALIDATION_ERROR",
  "message": "Параметр active должен быть одним из значений: all, active, inactive, 1, 0, true, false",
  "details": [
    { "field": "active", "issue": "invalid_value" }
  ]
}
```

| Код | Код ошибки | Когда |
|---|---|---|
| 200 | — | Успех |
| 400 | `VALIDATION_ERROR` | Некорректный `active`, `id_cardtype`, дата в `timestart`/`timeend`/`createdat`, `tabnum` длиннее 50 символов |
| 500 | `INTERNAL_ERROR` | Ошибка базы данных |

`404` для этих методов не используется: если по фильтру ничего не найдено,
возвращается `200` с пустым `context` или нулевыми счётчиками.

## Примеры (curl)

```bash
# Вся статистика по картам
curl -s "http://localhost:5056/api/v2/Identifier/GetCount"

# Статистика по типу 1 и активным картам
curl -s "http://localhost:5056/api/v2/Identifier/GetCount?id_cardtype=1&active=1"

# Карты сотрудника T-100, созданные 20.11.2026
curl -s "http://localhost:5056/api/v2/Identifier/GetList?tabnum=T-100&createdat=2026-11-20&pageIndex=0&pageSize=20"

# Карты, начало действия которых приходится на 25.11.2026
curl -s "http://localhost:5056/api/v2/Identifier/GetList?timestart=2026-11-25"

# Карты, действующие до конца 2026 года (точное значение TIMEEND)
curl -s "http://localhost:5056/api/v2/Identifier/GetList?timeend=2026-12-31%2023:59:59"

# Точное совпадение по номеру карты (прежний фильтр)
curl -s "http://localhost:5056/api/v2/Identifier/GetList?identifire=A1B2C3D4"
```

Проверить данные в базе:

```sql
SELECT c.ID_CARD, c.ID_CARDTYPE, p.TABNUM,
       c.TIMESTART, c.TIMEEND, c."ACTIVE", c.CREATEDAT
FROM CARD c
JOIN PEOPLE p ON p.ID_PEP = c.ID_PEP AND p.ID_DB = c.ID_DB
WHERE p.TABNUM = 'T-100'
ORDER BY c.ID_CARD;
```

## Совместимость

* Методы v1 (`/Identifier`) не изменялись.
* `GET /api/v2/Identifier/GetList` без новых параметров возвращает те же
  данные, что и до 1.8.0; новые поля ответа являются дополнением.
* `GET /api/v2/Identifier/GetCount` впервые появился в 1.8.0.
* Фильтр `identifire` сохранён как псевдоним точного фильтра по `ID_CARD`.
* `POST` и `DELETE /api/v2/Identifier` не изменялись.
